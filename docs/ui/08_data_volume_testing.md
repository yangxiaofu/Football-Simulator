# Step 8 — Data Volume Testing

**Status**: Drafted, pending review.
**Purpose**: Lock the performance discipline before code ships. Define budgets, test methodology, and the pre-launch gate so Phase 5 doesn't reach Steam release with a 4-second standings page.
**Inputs to this step**: Step 7 presenter shapes + no-caching policy, Step 5 build order, the data volumes implied by Phases 0-3 (32 teams, 1,696 players, multi-season stats, ~250-prospect draft classes).
**Output of this step**: Performance budgets per screen, fixture strategy, test methodology, virtualization rules, pre-launch performance gate.

---

## Why This Step Exists

Sim games fail two ways on performance:

1. **Slow common paths.** A 1.5-second Roster screen feels broken. Players navigate dozens of screens per session — even 200ms of latency compounds into a sluggish-feeling game.
2. **Sudden cliffs in late-game saves.** Year 1 has 1,696 active players. Year 10 has 1,696 active + ~10 × 250 retired/draft history + 10 × 17 × 16 × 8 = ~21,000 archived key plays. Screens that fly in Year 1 can stall in Year 10 if presenters aren't shaped for archive volume.

Both modes are caught by deliberate testing. Neither is caught by "feels fine on my machine in week 4."

You said "I want to ensure a good user experience" — that's exactly what this step protects.

## 1. Data Volume Reference

The numbers Phase 5 must hold up against:

| Object | Year 1 | Year 5 | Year 10 |
|---|---|---|---|
| Active players | 1,696 | 1,696 | 1,696 |
| Retired/historical players | 0 | ~1,500 | ~3,500 |
| Active contracts | ~1,696 | ~1,696 | ~1,696 |
| Historical contract years | 0 | ~6,000 | ~15,000 |
| Box scores per season | ~272 × 50 = ~13,600 | same | same |
| Box scores cumulative | ~13,600 | ~68,000 | ~136,000 |
| Key plays cumulative (8/game) | ~2,176 | ~10,880 | ~21,760 |
| Transaction log entries | ~500 | ~3,500 | ~7,500 |
| Awards records | ~100 | ~500 | ~1,000 |
| Draft prospects ever generated | ~250 | ~1,250 | ~2,500 |

The screens at most risk: **Stat Browser** (sweeps `player_career_stats` × all players ever), **League Leaders** (aggregates `player_season_stats` across 32 teams), **Transactions Log** (full history paginated), **Player Career Card** (career arc for retired players).

The screens at least risk: anything tied to current state (Roster, Standings, Cap, Schedule) — these scale with team or season constants, not history.

## 2. Performance Budgets

Each budget covers **end-to-end render time**: presenter execution + JSON serialization across bridge + JS render to first paint. Measured cold (no warmup) on a target spec.

**Target spec** (Steam minimum we design for): mid-range Windows 10/11 laptop, 8GB RAM, integrated graphics, NVMe SSD, WebView2 default.

| Screen Class | Budget (cold) | Budget (warm) | Rationale |
|---|---|---|---|
| **Context bar refresh** | < 50ms | < 30ms | Visible on every navigation; latency here = global feel |
| **Hub screens** (T-01 Dashboard, F-01 FO Hub) | < 100ms | < 60ms | Composite of multiple cards |
| **Roster, Player Card, Standings, Schedule** | < 100ms | < 60ms | Primary navigation surfaces |
| **Game Recap, Box Score** | < 150ms | < 80ms | Read-once screens, slightly more leeway |
| **League Leaders** | < 200ms | < 120ms | Aggregates across 32 teams |
| **Stat Browser** (filtered) | < 300ms | < 150ms | Largest list; virtualization helps the JS side |
| **Draft Class Browser** (~250 prospects) | < 200ms | < 100ms | Shouldn't need virtualization but watch closely |
| **Draft Room** (initial render) | < 250ms | < 150ms | Multi-pane composite |
| **Game sim batch** (32 games) | < 30 seconds | n/a | Engine-bound, not UI; tracked separately |

**Hard ceiling**: no screen ever exceeds 1 second cold. If any screen does, it gets fixed before that milestone closes.

**Why two columns (cold vs warm)?** Cold = first navigation to that screen this session. Warm = revisiting after the OS file cache and SQLite query plan are hot. Warm matters for daily play; cold matters for first impression.

## 3. Fixture Strategy

Golden file tests (Step 7) and performance tests both need deterministic data. Solution:

### `tests/fixtures/golden_franchise.db`

A frozen SQLite database committed to git, generated by `scripts/generate_golden_fixture.py`:

```python
# scripts/generate_golden_fixture.py
"""
Deterministic fixture generator. Produces the same DB byte-for-byte on every run.
Used by golden-file presenter tests and performance benchmarks.
"""
import random
random.seed(20260509)  # locked seed

# 1. Generate franchise (32 teams, 1,696 players, schedule)
# 2. Sim 10 full seasons through engine
# 3. Run offseasons (FA, draft, etc.) through Phase 3 systems
# 4. Write to tests/fixtures/golden_franchise_y10.db
```

Three named fixtures committed:

| Fixture | Description | Use |
|---|---|---|
| `golden_franchise_y1_w1.db` | Fresh franchise, week 1 | Smoke tests, primary screen verification |
| `golden_franchise_y1_w8.db` | Mid-season, multiple games played | Regular-season UI tests, Game Recap golden |
| `golden_franchise_y10.db` | 10 seasons of history | **Volume tests** — Stat Browser, Career Card, Transaction Log |

**Regeneration policy**: only on intentional schema migrations. Each regeneration is a separate, reviewed commit (golden files are the test contract).

## 4. Test Methodology

### 5.1 Presenter Microbenchmarks

Every presenter has a perf test alongside its golden test:

```python
# src/ui/tests/test_presenters_perf.py
import time
from src.ui.presenters import roster

def test_roster_perf():
    conn = open_fixture("y1_w1")
    runs = [_time(lambda: roster.build(conn, team_id=1)) for _ in range(20)]
    median_ms = sorted(runs)[10] * 1000
    assert median_ms < 100, f"Roster presenter exceeded 100ms: {median_ms:.1f}ms"
```

Run on every CI build. Fails the build if any presenter exceeds its budget.

### 5.2 End-to-End Render Tests (manual at v1)

Open the actual UI in `--debug` mode, use Chrome DevTools Performance profiler, navigate the 5 user flows from Step 1, capture flame graphs. Look for:

- Bridge call latency (the gap between JS request and Python response).
- DOM render time (Alpine reactivity, table rendering).
- Layout thrash (multiple reflows on a single navigation).

Manual at v1 because automated headless testing of a pywebview app is a setup tax that doesn't pay back at this scale.

### 5.3 Volume Tests Against Year-10 Fixture

Repeat the perf microbenchmarks against `golden_franchise_y10.db`. Most presenters should be unchanged (their queries don't widen with history). Watch closely:

- `presenters.player.build()` for retired players (career-spanning data).
- `presenters.dynasty.build_hub()` (all-time records).
- `presenters.stat_browser.build()` (career stats sweep).
- `presenters.transactions.build_log()` (cumulative log).

If any cross its budget against the Year-10 fixture, fix before declaring that milestone done.

### 5.4 Long-Session Soak Test

Manual, once per phase: open the UI, run 16 full weeks of sim with no restart, then check:

- Memory growth (DevTools Memory tab — should stabilize, not climb).
- Save file size growth (compare before/after).
- DB query plan stability (`EXPLAIN QUERY PLAN` on the heaviest queries — make sure indexes are still being used).

A 30-minute soak test surfaces leaks and N+1 patterns that microbenchmarks miss.

## 5. Virtualization Rules

| Row Count | Rendering Strategy |
|---|---|
| **≤ 100 rows** | Render full. No virtualization. Simplest code. |
| **100–500 rows** | Render full but lazy-attach detail panels. Keep it simple. |
| **> 500 rows** | **Virtualize**. Only render visible rows + buffer. |

The only screen currently in the > 500 category is **Stat Browser** when filtering across all players ever (~3,500+ at year 10).

### Implementation choice (deferred)

Two approaches:
- **Custom**: ~80 lines of vanilla JS using Intersection Observer to render row chunks.
- **Library**: AG-Grid Community (production-ready) or a lighter alternative.

Decision deferred until the Stat Browser is built (Milestone 5.4). If custom virtualization works fine, ship it. If it stutters, drop in AG-Grid Community for that one screen — every other list keeps its vanilla `<table>`.

## 6. Common Bottleneck Patterns to Watch

These are the failure modes most likely to surface, in roughly decreasing order of likelihood:

### N+1 Queries
**Pattern**: presenter loops through 53 players and calls `queries.get_contract(player_id)` inside the loop.
**Fix**: extend `queries.get_team_roster()` to JOIN contracts.
**Detection**: `EXPLAIN QUERY PLAN` showing the same query repeated; query log showing 53+ queries on a single roster render.

### Unindexed Scans
**Pattern**: `WHERE season_year = 2026 AND player_id = 421` on a 100,000-row stat table without a compound index.
**Fix**: add index in schema; document in `docs/GDD_Layer3_DataModel.md`.
**Detection**: `EXPLAIN QUERY PLAN` shows `SCAN TABLE` instead of `SEARCH TABLE USING INDEX`.

### Synchronous Heavy Work in Bridge Calls
**Pattern**: `do_advance_week()` blocks for 4 seconds while simming 16 games. UI freezes.
**Fix**: long-running work returns a task ID; JS polls for progress (per Step 5 bridge contract).
**Detection**: any `do_*` call exceeding 500ms.

### Oversized JSON Across Bridge
**Pattern**: `get_stat_browser()` returns 3,500 player rows × 50 stat columns = ~5MB JSON.
**Fix**: server-side filter+sort+paginate; pass page size and offset.
**Detection**: bridge response time scales with data size linearly.

### Layout Thrash on Render
**Pattern**: each Alpine `x-for` triggers a separate reflow; 53 player rows = 53 reflows.
**Fix**: batch DOM updates, use `display: contents` or virtualization.
**Detection**: DevTools shows multiple "Layout" entries per navigation.

## 7. Pre-Launch Performance Gate

Before declaring v1 ready for Steam:

- [ ] All presenters under budget against `golden_franchise_y1_w1.db`.
- [ ] All presenters under budget against `golden_franchise_y10.db`.
- [ ] No screen exceeds 1 second cold render against either fixture.
- [ ] Game sim batch: 16 games complete in under 15 seconds (target 1 second/game).
- [ ] Memory stable across a 30-minute soak test (no monotonic growth > 50MB).
- [ ] No `EXPLAIN QUERY PLAN` returns `SCAN TABLE` for any query touched by a primary screen.
- [ ] Stat Browser renders 1,696 active player rows in < 500ms first paint.
- [ ] Continue button responsiveness: from click to first visual response < 100ms (long sim flips to progress UI immediately).

If any criterion fails, that's the Phase 5 closer — fix before declaring complete.

## 8. What Performance Testing Does NOT Cover

These are real concerns, but live elsewhere:

- **Sim correctness** (engine produces realistic stats) — Phase 1 tuning concern.
- **AI quality** (AI GMs make sensible trades) — Phase 3 concern.
- **Visual fidelity** (recap screens look polished) — Step 9 concern.
- **Cross-platform parity** (Mac/Linux behavior) — out of scope; Steam Windows is the launch target.
- **Network** (no online features in v1).

Step 8 owns latency and throughput on the local single-player loop. Nothing else.

---

## 9. Implementation Note: When to Run Step 8 Tests

Performance tests run at three points in Phase 5:

| Point | What runs | What gates |
|---|---|---|
| **Per milestone** | Microbenchmarks for that milestone's presenters | Don't close milestone if presenter exceeds budget |
| **End of Milestone 5.4** (Viewer Build) | Full presenter suite + manual user-flow profiling | Decide whether to course-correct before wiring actions |
| **Pre-launch (end of 5.12)** | Full pre-launch gate from §7 | Required to ship |

The intermediate performance check at 5.4 is the single most valuable one — it catches systemic problems (N+1 patterns, missing indexes) when the cost to fix is low.
